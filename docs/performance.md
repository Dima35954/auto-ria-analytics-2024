# Профілювання та оптимізація продуктивності

## 1. Інструменти профілювання
Для аналізу продуктивності клієнтського застосунку на базі Flutter використовуються вбудовані інструменти **Flutter DevTools**:
* **Performance View (CPU Profiler):** Для вимірювання часу виконання функцій ядра (`AnalyticsEngine`) та виявлення затримок рендерингу UI (UI jank).
* **Memory View:** Для відстеження витоків пам'яті (Memory leaks) та аналізу Heap-пам'яті під час обробки великих масивів даних.
* **Network View:** Для аналізу часу завантаження статичних ассетів (оскільки база даних локальна, цей інструмент використовується базово).

## 2. Ключові метрики продуктивності
* **Час виконання (Execution Time):** Час у мілісекундах (мс), необхідний для обробки даних аналітичним ядром.
* **Споживання пам'яті (Memory Usage):** Обсяг оперативної пам'яті (МБ), виділений під масиви об'єктів `CarListing`.
* **Час побудови кадру (Frame Build Time):** Повинен бути < 16 мс для забезпечення плавних 60 FPS.

## 3. Тестові сценарії (Стрес-тест)
Для отримання репрезентативних даних було створено набір Mock-даних обсягом **50 000 записів** автомобілів.
**Сценарій:** Користувач відкриває головний дашборд, що викликає одночасне виконання трьох важких аналітичних функцій: пошук найпопулярніших марок, розрахунок середньої ціни та складну фільтрацію.

---

## 4. Базове профілювання та "Гарячі точки" (До оптимізації)

Запуск CPU Profiler виявив 3 критичні "гарячі точки" (bottlenecks), які викликали "зависання" UI на 450+ мс.

### Гаряча точка 1: Розрахунок популярних марок (`getTopBrands`)
* **Проблема:** Використовувався вкладений цикл (алгоритмічна складність O(N^2)). Для кожної унікальної марки програма заново проходила по всьому масиву з 50 000 записів через метод `.where()`.
* **Час виконання:** 320 мс.

### Гаряча точка 2: Розрахунок середньої ціни (`calculateAveragePrices`)
* **Проблема:** Усередині циклу для кожного автомобіля створювався новий екземпляр класу `NumberFormat` та `DateTime` для парсингу рядків. Це спричиняло надмірне навантаження на Garbage Collector.
* **Час виконання:** 145 мс.

### Гаряча точка 3: Фільтрація за критеріями (`filterCarsByCriteria`)
* **Проблема:** Використовувався ланцюжок методів `.where().toList().map().toList()`. Кожне викликання `.toList()` створювало новий проміжний масив у пам'яті на десятки тисяч елементів.
* **Час виконання:** 85 мс.
* **Споживання пам'яті (пікове):** 112 МБ.

## 5. Оптимізація та Повторне профілювання (100%)

Було проведено рефакторинг коду. Після цього проведено повторний замір через Flutter DevTools.

### Оптимізація 1 (Алгоритмічна)
* **Рішення:** Заміна O(N^2) на O(N). Замість вкладених циклів використано структуру даних `HashMap` для підрахунку частоти в один прохід (`fold`).
* **Новий час:** 12 мс.
* **Покращення:** **96.2%**

### Оптимізація 2 (Кешування інстансів)
* **Рішення:** Екземпляри `NumberFormat` та `DateFormat` винесено за межі циклу як статичні/константні змінні.
* **Новий час:** 25 мс.
* **Покращення:** **82.7%**

### Оптимізація 3 (Ліниві обчислення / Lazy Iterables)
* **Рішення:** Видалено проміжні виклики `.toList()`. Використано ліниві ітератори `Iterable`, і лише фінальний результат конвертується у `List`.
* **Новий час:** 15 мс.
* **Споживання пам'яті (пікове):** Зменшилось до 45 МБ.
* **Покращення:** **82.3%** швидкодії та **-60%** споживання RAM.

## Висновок
Завдяки профілюванню за допомогою Flutter DevTools загальний час обробки стрес-тесту (50 000 записів) було зменшено з **550 мс** до **52 мс** (загальне покращення у понад 10 разів). Це повністю усунуло проблему пропуску кадрів (UI jank), забезпечивши плавний рендеринг у 60 FPS. Нових критичних "гарячих точок" після оптимізації не виявлено.
